# Plano de Otimização AdminDashboard

## Objetivo
Transformar o AdminDashboard de um componente monolítico e pesado em uma aplicação mais rápida, mantendo a mesma funcionalidade.

## Problemas Atuais (a resolver)

1. **fetchData() muito pesado**: Carrega tudo de uma vez no inicial
2. **Falta useCallback**: Handlers recriados a cada render causando re-renders
3. **Sem cache inteligente**: Usa `cache: 'no-store'` para tudo
4. **Todas tabs renderizadas**: Mesmo as não visíveis consomem recursos
5. **Mais de 20 useState**: Componente muito pesado
6. **Listas sem paginação**: `.map()` direto em arrays grandes (logs, aldeias, transacoes)

## Estratégia de Execução (4 Fases)

### FASE 1: useCallback e Separação Dados ⭐ (PRIORIDADE ALTA)

**Ação**: Adicionar useCallback a todos os handlers principais e separar fetch em dados essenciais vs secundários.

**Arquivo**: `src/features/admin/admin-dashboard.tsx`

**Mudanças**:
- [ ] `fetchData()`: usar `next: { revalidate: X }` em vez de `cache: 'no-store'`
  - Dados essenciais (stats, eventos, jogos): revalidate 20-30s
  - Dados secundários (logs, transacoes): revalidate 60s+ ou usar SWR
  - Separar em `fetchEssentialData()` e `fetchSecondaryData()`
- [ ] `handleSaveEvento`: useCallback, dependências mínimas
- [ ] `handleSaveJogo`: useCallback  
- [ ] `handleToggleJogoEstado`: useCallback
- [ ] `handleSaveUser`: useCallback
- [ ] `handleSaveAldeia`: useCallback
- [ ] `handleConvertPrize`: useCallback
- [ ] `executeDelete`: useCallback
- [ ] `handleExecutarSorteio`: useCallback
- [ ] `requestDelete`: não precisa useCallback (não recriado por deps)

**Critério de parada**: Todos os handlers que chamam fetchData ou mudam estado importante devem ter useCallback.

### FASE 2: Lazy Loading das Tabs ⭐⭐ (PRIORIDADE ALTA)

**Ação**: Extrair TabsContent pesadas para componentes separados e carregar com lazy + Suspense.

**Arquivos a criar**:
- `src/features/admin/tabs/TabAnalytics.tsx`
- `src/features/admin/tabs/TabTransacoes.tsx`
- `src/features/admin/tabs/TabAldeias.tsx` (se for pesada)
- `src/features/admin/tabs/TabAuditoria.tsx`

**Mudanças no AdminDashboard**:
```typescript
import dynamic from 'next/dynamic';

const TabAnalytics = dynamic(() => import('./tabs/TabAnalytics'), {
  loading: () => <Skeleton className="h-96" />,
  ssr: false
});

const TabTransacoes = dynamic(() => import('./tabs/TabTransacoes'), {
  loading: () => <Skeleton className="h-96" />,
  ssr: false
});
```

**O que move para components separados**:
- TabAnalytics: Tudo do analytics (DashboardAnalytics + stats adicionais)
- TabTransacoes: Lista de transações + filtros próprios
- TabAldeias: CRUD de aldeias completo
- TabAuditoria: Lista de logs + paginação

**Benefício**: Redução massiva do bundle JS inicial (cerca de 40-50% menor)

### FASE 3: Paginação Real nas Listas ⭐⭐ (PRIORIDADE MÉDIA)

**Ação**: Adicionar paginação/infinite scroll nas listas grandes.

**Componentes afetados**:
- TabAnalytics: Logs (já tem limite? verificar)
- TabAldeias: Lista de aldeias
- TabTransacoes: Lista de transações
- Overview: Eventos recentes (talvez manter como está)

**Abordagem**:
```typescript
const ITEMS_PER_PAGE = 20;
const [page, setPage] = useState(1);

const paginatedItems = items.slice((page - 1) * ITEMS_PER_PAGE, page * ITEMS_PER_PAGE);

return (
  <>
    {paginatedItems.map(item => ...)}
    <Pagination 
      page={page}
      totalPages={Math.ceil(items.length / ITEMS_PER_PAGE)}
      onPageChange={setPage}
    />
  </>
)
```

**Alternativa melhor**: Usar API do backend com `?page=X&limit=Y` e buscar só o necessário

## Dependências e Riscos

### O que pode quebrar
- Refatorar handlers pode quebrar closures (cuidado com dependências no useCallback)
- Lazy loading pode causar hydration mismatch no Next.js (usar `ssr: false`)
- Separar tabs pode quebrar acesso a estados locais (precisa passar via props/context)

### Mitigação
- Manter estados globais no componente pai quando necessário
- Testar build completo antes de commit
- Fazer commit incremental (fase a fase)

## Critérios de Aceite

✅ Build passa sem erros
✅ Lighthouse performance > 80 (era ~40 antes)
✅ Sem warnings de React no console
✅ Todas funcionalidades originais mantidas
✅ Tempo de carregamento inicial < 2s
